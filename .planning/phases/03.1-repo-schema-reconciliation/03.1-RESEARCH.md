## Schema Merge Strategy

### §4.1 Approach: `prisma migrate diff` from origin/production schema → local schema

Do NOT hand-author the migration. Use Prisma's built-in differ to generate exact DDL from the schema delta. Command:

```bash
cd backend
npx prisma migrate diff \
  --from-schema-datasource <(git show origin/production:backend/prisma/schema.prisma) \
  --to-schema-datasource prisma/schema.prisma \
  --script > /tmp/phase04-migration.sql
```

**Why migrate diff (not hand-write):**
1. Avoids the `EmailTemplate.category ADD COLUMN` trap — Prisma sees the column already in `--from` (it IS in origin/production schema), so it only emits the new index DDL
2. Generates correct constraint/index naming aligned with Prisma 5.4.2 conventions
3. Handles the `@unique` constraints on apolloPersonId / apolloOrgId via Prisma's standard `CREATE UNIQUE INDEX "{Model}_{field}_key"` naming
4. Safe to re-run — deterministic output

**Expected output (preview):**
```sql
-- AlterTable Contact
ALTER TABLE "contacts" ADD COLUMN "stream" TEXT;
ALTER TABLE "contacts" ADD COLUMN "apolloPersonId" TEXT;
ALTER TABLE "contacts" ADD COLUMN "apolloRawData" JSONB;

-- CreateIndex
CREATE UNIQUE INDEX "contacts_apolloPersonId_key" ON "contacts"("apolloPersonId");
CREATE INDEX "contacts_stream_idx" ON "contacts"("stream");
CREATE INDEX "contacts_apolloPersonId_idx" ON "contacts"("apolloPersonId");

-- AlterTable Company
ALTER TABLE "companies" ADD COLUMN "stream" TEXT;
ALTER TABLE "companies" ADD COLUMN "apolloOrgId" TEXT;
ALTER TABLE "companies" ADD COLUMN "apolloRawData" JSONB;

-- CreateIndex
CREATE UNIQUE INDEX "companies_apolloOrgId_key" ON "companies"("apolloOrgId");
CREATE INDEX "companies_stream_idx" ON "companies"("stream");
CREATE INDEX "companies_apolloOrgId_idx" ON "companies"("apolloOrgId");

-- CreateIndex on email_templates.category (column already exists)
CREATE INDEX "email_templates_category_idx" ON "email_templates"("category");
```

## Pitfalls

### §7.1 EmailTemplate.category column already exists (HANDLED IN §4)

If the plan tries to hand-write `ALTER TABLE email_templates ADD COLUMN category TEXT;` it will fail with `column "category" of relation "email_templates" already exists`. Mitigation: use `prisma migrate diff` which sees the column on both sides and only emits `CREATE INDEX`.

### §7.2 Prisma version mismatch

- Local backend `package.json`: `prisma ^5.4.2`, `@prisma/client ^5.22.0`
- EC2 deployed: `prisma ^5.4.2`, `@prisma/client ^5.22.0` (verified)
- No mismatch. No `prisma generate` cross-version concerns.

### §7.3 Migration checksum validation

When `prisma migrate deploy` runs against the prod DB after Phase 03.1's push, it will validate that the checksum of each `migration.sql` file matches what's stored in `_prisma_migrations.checksum`. Since we are scp-ing the EXACT bytes from EC2 (the same files Prisma read when it originally applied them), checksums should match. **If they don't:** the file may have CRLF-vs-LF differences from when it was originally applied. Mitigation: `tar -czf` (used in §5.1) preserves byte-for-byte; `scp -r` should also. Verify with `prisma migrate status` (Wave 4).

### §7.4 Origin diverged during 03.1 work

If `origin/production` advances during 03.1 work (unlikely in active sole-developer session, but possible if a CI bot or other clone pushes), the final `git push` will be rejected as non-fast-forward. Mitigation:
```bash
git fetch origin production
git rebase origin/production  # linear rebase — no merge commit
git push origin production
```
NOT `--force-push`. If rebase produces conflicts, that's a real divergence to investigate — pause the plan.

### §7.5 Stray `backend/schema.prisma` on EC2

EC2 has both `backend/prisma/schema.prisma` (what Prisma uses, matches origin/production) and `backend/schema.prisma` (orphan, modified, never read). Phase 03.1 does NOT touch EC2 — this stays as-is. Document for future hygiene; do not mutate during reconciliation.

### §7.6 The 17 EC2-only migrations contain DDL that's already applied

The migration files describe DDL like `ALTER TABLE contacts ADD COLUMN voiceUrl TEXT` that the prod DB already has. After scp, running `prisma migrate deploy` against prod must NOT re-execute that DDL. Prisma protects against this via the `_prisma_migrations` table presence check (each migration's row marks it `finished_at NOT NULL`). Verified: all 17 have rows. Plan should add a `prisma migrate status` dry-run before any deploy.

### §7.7 `.gitignore` for `*.sql` files

From Phase 4 SUMMARY: `backend/.gitignore` line 49 ignores `prisma/migrations/**/*.sql`. The Phase 4 audit SQL was force-added (`git add -f`). The 17 backfilled migration SQL files will need the same treatment. Plan must include `git add -f backend/prisma/migrations/*/migration.sql` in Wave 2 commit step.

### §7.8 Phase 4 Wave 4 deploy interaction with 03.1

Phase 4 Wave 4 (deploy + smoke) runs AFTER 03.1 ships. The CI workflow (`.github/workflows/deploy-*.yml` per memory note about `deploy.sh` paths) runs:
1. `prisma migrate deploy` — applies pending migrations

## Rollback Plan

### §10.1 If reconciliation fails mid-flight

The backup branch `backup/pre-3.1-production-state` captures pre-work state. To revert:

```bash
# Abandon current work branch
git checkout production
git branch -D sync/03.1-reconcile-with-ec2

# Reset production back to backup
git reset --hard backup/pre-3.1-production-state

# If you already pushed bad state, force-push reset (RARE — push requires unusual failure mode)
git push --force-with-lease origin production
```

**Note on --force-with-lease vs --force:** Use `--force-with-lease` always — it's a soft force that aborts if origin/production has advanced beyond what your local `origin/production` ref tracked. Prevents stomping on concurrent pushes.

### §10.2 If `prisma migrate diff` produces unexpected output

The Phase 4 audit SQL at `backend/prisma/migrations/manual/04-add-stream-and-apollo-fields.sql` is the canonical DDL spec. If migrate diff fails or emits wrong DDL, fallback to manual migration:
