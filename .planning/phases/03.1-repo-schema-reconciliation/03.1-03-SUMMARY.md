**1. [Rule 3 - Blocking] `prisma migrate diff` emitted redundant `ADD COLUMN "category"` for email_templates — would fail at prod deploy**

- **Found during:** Task 1 Step 4 (smoke-read generated SQL)
- **Issue:** `prisma migrate diff` correctly computed the column-delta between origin/production schema (no `category` field) and local schema (has `category` field at line 510). The generated migration included `ALTER TABLE "email_templates" ADD COLUMN "category" TEXT;`. However, RESEARCH §2.1 verified via `information_schema.columns` query that the column **already exists in prod DB** (it predates Phase 4 — the Phase 4 work only added the `@@index([category])` directive, not the column itself). Running this migration against prod via `prisma migrate deploy` would fail with `column "category" of relation "email_templates" already exists`.
- **Fix:** Followed the fallback path documented in Plan 03 lines 138-159 + RESEARCH §10.2. Used inline Python `re.sub` to strip the standalone `-- AlterTable\nALTER TABLE "email_templates" ADD COLUMN "category" TEXT;\n` block while preserving `CREATE INDEX "email_templates_category_idx" ON "email_templates"("category");`. Verified post-strip: 0 `ADD COLUMN "category"` matches, 1 `email_templates_category_idx` match.
- **Files modified:** Only the in-flight `/tmp/phase04-migration.sql` (before being moved into the migration tree)
- **Verification:** `grep -c 'ADD COLUMN "category"' migration.sql` → 0; `grep -c 'email_templates_category_idx' migration.sql` → 1
- **Committed in:** `a5872fd` (the migration commit itself; commit message documents the strip)
- **Why this is auto-fix not user-ask:** This was the exact trap RESEARCH §7.1 + Plan 03 lines 110-116 + Plan 03 fallback (lines 138-159) anticipated. The fix is mechanical (regex strip) and prescribed in the plan. No architectural decision required.

**2. [Rule 3 - Blocking] `prisma format` mutated stray `backend/schema.prisma` orphan because Prisma 5.4.2 prefers cwd `./schema.prisma` over `./prisma/schema.prisma`**
